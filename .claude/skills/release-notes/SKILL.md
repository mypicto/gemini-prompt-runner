# Release Notes (gemini-prompt-runner)

Chrome ウェブストアの掲載文にある「リリースノート」を、**過去の版と同じ書式・文体**で、
**日本語と英語の両方**に生成する。生成するのは**最新バージョンのブロックだけ**。
読者は拡張機能のユーザーなので、**コミット単位の内部事情ではなく、ユーザーが体感する変化**を書く。

過去の実例(トーンの正解)は `references/store-listing.md`。文体に迷ったら必ず参照する。

## 出力フォーマット

日本語と英語を **それぞれ独立したコードブロック** に分けて出力する(日本語が先)。
貼り付け先(ストアの言語別の掲載欄など)が別々なので、一方だけをそのままコピーできるようにする。
両者を1つのコードブロックにまとめない。

日本語:

```
リリースノート (verX.Y.Z)：

- <変更1>
- <変更2>
```

英語:

```
Release Notes (verX.Y.Z):

- <change 1>
- <change 2>
```

- ヘッダのコロンは **日本語=全角「：」/ 英語=半角「:」**。バージョンは `verX.Y.Z` 表記。
- 日英は **同じ変更集合・同じ順序**(1対1)。片方だけに項目がある状態にしない。
- 箇条書きは `- `。1変更1行。

## 文体ルール (コーパスから抽出)

なぜこう書くか: ストアの読者は開発者ではなくユーザー。彼らにとって意味があるのは「何が直ったか/
何ができるようになったか」であって、TypeScript 化や関数名ではない。だから**可観測な挙動**を、
短く言い切る。

- **ユーザー視点の可観測な変化**を書く。DOM セレクタ名・クラス名・内部モジュール名は出さない
  (例: 「送信ボタンのセレクタを修正」ではなく「プロンプトを送信できない不具合を修正」)。
- **内部だけの変更**(リファクタ・ビルド基盤・テスト等)は原則**省略**。まとめて言及する価値が
  あるときのみ「内部設計の改善。」/ "Improved the internal design." の **1行に集約**。
- **不具合修正**: 日本語「〜不具合を修正。」「〜問題を修正。」「〜ケースを修正。」/
  英語 "Fixed an issue where …."
- **機能追加・変更**: 日本語「〜を追加」「〜に対応。」「〜するよう変更。」「〜を表示。」/
  英語 "Added …", "Supports …", "Updated …", "Introduced …", "Displayed …"(過去形基調)。
- パラメータ・キーワード・記号は**コード表記**(`ext-send`, `ext-q`, `ext-m`, `{{clipboard}}`, `#`)。
- 製品名は **"Google Gemini" / "Gemini"**。コーパス日本語側に "Gemuni" という誤記があるが
  **再現しない**。
- 簡潔・事実ベース。宣伝文句や誇張は入れない。関連する複数コミットは **1行に統合**。
- 並び順の目安: **新機能 → 不具合修正 →(あれば)内部**。

## 生成手順

1. **対象バージョンを決める**: 既定は `public/manifest.json` の `version`。ユーザー指定があれば従う。
2. **変更を集める**: 直前のリリースを `gh release list` / `git tag` で特定し、
   `git log <前リリースタグ>..HEAD --oneline` を読む。挙動が判然としないコミットは差分も確認する。
   ユーザーが変更点を口頭で提示した場合は、それを一次情報として優先。
3. **分類して絞る**: 各変更を「ユーザー向け機能」「ユーザー向け修正」「内部のみ」に仕分け。
   内部のみは落とすか1行に集約。重複・関連は統合(例: 同種のセレクタ修正が複数コミットに
   分かれていても1行)。
4. **日本語を起案 → 英語へ**: 文体ルールに沿って日本語のノートを作り、**同じ項目・同じ順序**で
   英語に直す(逐語訳ではなく英語側の定型に合わせる)。
5. **最新版ブロックのみ出力**。説明文・機能一覧・帰属は触らない。

## 例 (コーパスより)

**例1: 機能と修正の混在 (ver1.5.0)**
コミット要旨: クエリ形式にフラグメント推奨メッセージ表示 / URL 生成オプションの状態記憶 /
内部リファクタ多数 / 全角括弧付きモデル名で切替できない修正
→ 内部リファクタは「内部設計の改善。」1行に集約し、機能→内部→修正で列挙:
```
リリースノート (ver1.5.0)：

- クエリパラメータ形式でのパラメータ指定に対して、フラグメント形式を推奨するメッセージを表示。
- URL生成オプションの選択状態を記憶するように変更。
- 内部設計の改善。
- モデル名に全角の括弧が使われていた場合に、モデル名を完全一致させないとモデルを切り替えられない問題を修正。
```

**例2: 修正のみ・内部語を出さない (ver1.6.3)**
コミット要旨: TrustedHTML 対応で textarea 入力を修正 / Gemini UI 変更でセレクタ更新
→ 内部の仕組みではなくユーザーが見える結果で言い切る(日英は別ブロック):
```
リリースノート (ver1.6.3)：

- Gemini の TrustedHTML 制約により、プロンプトをテキストエリアに入力できない不具合を修正。
- Google Gemini のUI変更に追従し、モデル選択ボタンなどのセレクタを更新。
```
```
Release Notes (ver1.6.3):

- Fixed an issue where prompts could not be entered into the text area due to Gemini's TrustedHTML restrictions.
- Updated selectors such as the model selection button to keep up with changes to the Google Gemini UI.
```
